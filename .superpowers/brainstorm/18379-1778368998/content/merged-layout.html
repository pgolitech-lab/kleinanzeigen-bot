A · История сверху, action-bar снизу

Pros: хронология читается естественно (старое→новое→draft→акт). Mobile-friendly: action-grid там где обычно поле ввода. Похоже на bot-карточку — оператор привычен.
Cons: длинный тред = много прокрутки до actions. Решается sticky-bottom для action-bar (всегда внизу viewport, история скроллится под ним).

B · Action-секция сверху, история ниже

Pros: primary task (draft + acts) виден без скролла. Если нет pending — секция отсутствует, история занимает весь экран. Если pending — оператор сразу видит что отправлять.
Cons: история становится «контекст», иногда теряет важное (last incoming уже вынесен в action-секцию). Часть thread-events дублируется. Может быть collapsible.

Multi-pending в треде

Оба варианта показывают самый свежий pending msg_id в action-секции. Старые pending видны в истории как нормальные incoming-events с маркером 📝 (но не имеют action-grid). Оператор обработал свежий → screen refreshит → следующий по свежести становится active. Если нужно открыть конкретный старый pending вручную — link на /review/{msg_id} (deep route, который рендерит ту же merged-страницу но фокусирует на этот msg_id).
